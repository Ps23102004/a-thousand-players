# ReproBot fresh play

The committed JSON is a placeholder until a run is performed. The experiment uses the report and oracle in `data/samples/repro.json`, the current default game rules, and fresh seeds checked against both recorded run files. It drives the player against the normal CPU. Every 12 ticks it chooses an action; successful answers are cached by the existing spotlight observation key. Each round stops when the entire oracle first matches or when the round ends. The first match time is the simulation time at which all conditions hold, not the time of the earliest contributing event. The oracle inherits the engine's 220-event cap.

The lead can run the real experiment separately, with their existing model credentials in the environment, using `node --import tsx ai/cli/reprobot.ts --out /tmp/reprobot-results.json`. At most 40 calls are attempted, including failed responses; `--max-calls` can lower that limit. Once an uncached observation needs a call beyond the cap, the current round is marked incomplete and the run stops. Successful cached actions remain available without calls. Fallbacks are not cached. A high fallback count means the model may not have been available and must not be interpreted as a passive Nano player.

Import a reviewed output with `node --import tsx ai/cli/reprobot.ts --results-from /path/to/results.json`. The importer checks seeds, counts, and totals before replacing `data/reprobot/results.json`. `--out` chooses a different output path. `--dry-run` prints the plan without playing or writing, and `--fake-model` runs offline using a fixed action; fake results are explicitly labeled. Neither mode establishes a Nano result. For a complete run the block reports the reproductions among 20 completed rounds; if the budget stops it early, it reports the actual number completed and the number planned. It is one report and one run, not a success rate or evidence that the bug is absent. No live result has been produced in this worktree.
