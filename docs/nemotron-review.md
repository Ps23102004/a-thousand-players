# Nemotron Review: Models Propose, Code Checks

This pipeline implements a multi-stage, self-auditing architecture where NVIDIA Nemotron models review proposals generated by Nemotron models, with deterministic TypeScript code serving as the final ground-truth verification boundary ("models propose, code checks").

The review covers two critical offline evaluation tracks:
1. **`drift-judge`**: Nemotron Ultra acts as an independent second-model judge evaluating the 8 verified architectural drift claims between design documents and game source code, comparing against the earlier Gemini evaluations with Cohen's kappa inter-rater reliability.
2. **`aid-fix`**: Nemotron Super and Nemotron Ultra collaborate to audit and correct tutorial aids drafted for struggling players, ensuring that every structured number, percentage, and control key is strictly factual and consistent with game rules and control definitions.

---

## Architectural Design

### Principle: Models Propose, Code Checks
LLMs excel at synthesizing natural language explanations, proposing candidate categorizations, and refining instructional phrasing. However, language models frequently hallucinate non-existent controls, miscalculate complementary percentages (such as confusing a $0.15$ multiplier with an $80\%$ reduction rather than $85\%$), or provide plausible-sounding justifications unsupported by actual code.

In this architecture:
- **No model assertion is taken on faith.**
- **Code computes mathematical and structural ground truth** before any model is invoked.
- **Code verifies model outputs** via strict regular expressions, substring matching, whitelist verification, and numerical equivalence.
- **Model outputs are rejected and retried** when code or reviewer checks fail, with a hard-stop limit of one retry per item.
- **`data/tutor/results.json` is strictly read-only**: the original benchmark tutor measurements remain intact and uncorrupted; all rewritten aids reside exclusively in `data/nemotron-review/aid-fix.json`.

## Mode 1: `drift-judge`

### Pipeline
1. **Source Loading**:
   - Reads the 8 verified claims from `data/drift/results.json` (`docClaim`, `docFile`, `codeFile`, `codeSymbol`, `codeLine`, `whatCodeDoes`).
   - Reads the earlier second-model judgments from `data/drift/judge.json` (evaluated by Gemini 3.8 Flash).
2. **Context Window Extraction**:
   - For each cited code file and line number, code extracts an exact snippet bounded by $\pm 12$ lines around the target line, with line numbers attached and whitespace trimmed.
   - For each cited document quote, code locates the verbatim text in `docs/design.md` or `game/README.md` and extracts $\pm 12$ lines around the quote.
3. **Model Evaluation**:
   - Exactly **ONE** Ultra call (`nvidia/Nemotron-3-Ultra-550b-a55b`) with `thinking: false`, `temperature: 0.2`, `timeoutMs: 10 * 60_000`, `retries: 0`.
   - The model must categorize each claim into exactly one of three enums:
     - `REAL_DRIFT`: The source code directly contradicts an explicit specification or contract in the design document.
     - `DOC_VAGUE`: The document is high-level, informal, or ambiguous, and the implementation is a reasonable interpretation or natural elaboration rather than a bug or contradiction.
     - `NOT_DRIFT`: There is no contradiction; the claim misinterprets the code, misreads the document, or conflates separate systems.
   - For every verdict, the model must provide a one-sentence reason that quotes a code line.
4. **Code Validation**:
   - Enforces **exactly 8 verdicts** corresponding to claims 1 through 8.
   - Enforces valid enum values (`REAL_DRIFT`, `DOC_VAGUE`, `NOT_DRIFT`).
   - **Support check (`isReasonSupported`)**: Verifies that every reason quotes a code line or contains a verbatim substring that occurs in the cited code or doc excerpt. Any reason failing this test is flagged as `supported: false` and tallied in `unsupportedCount`.
   - **Agreement & Cohen's Kappa**: Computes the count of agreements and disagreements with the Gemini verdicts by claim, and calculates Cohen's kappa ($\kappa = \frac{p_o - p_e}{1 - p_e}$).
5. **Output**:
   - Atomically written to `data/nemotron-review/drift-judge.json`.

## Mode 2: `aid-fix`

### Pipeline
For each of the 3 tutorial aids in `data/tutor/results.json`:
1. **Ground Truth Fact Computation (Code)**:
   - Derives all permissible numbers and percentages from `aid.tuningOverrides`. For example, for `rules.guardDamageMultiplier = 0.15`:
     - Multiplier = $0.15$
     - Direct percentage = $15\%$
     - Damage reduction percentage = $(1 - 0.15) \times 100\% = 85\%$
     - Damage reduction value = $0.85$
   - Extracts official control definitions and control keys from `game/index.html` (e.g. keyboard keys `A, D, J, K, S, L, F, H, Q, V, W, E, R, G, ESC, ENTER` and control numbers like `4` for punch chain, `3` for kick chain).
2. **Super Rewrite**:
   - One Super call (`nvidia/nemotron-3-super-120b-a12b`) per aid is asked to rewrite `playerFacingText` so that every mentioned number and key matches the computed facts and official game controls, without inventing non-existent controls.
3. **Code Checks**:
   - **Number Check**: Extracts all numbers, percentages, and number words from the rewrite text. Every number must match an allowed computed fact or game control number. An invalid percentage (e.g., repeating the buggy "80%" when the override gives 85%, or claiming a 5-punch chain) is rejected immediately.
   - **Key Check**: Verifies that every control key mentioned exists in the game's official controls. Mentions of non-existent keys (e.g. `X`, `Z`, `Shift`, `Space`) are rejected immediately.
   - Tally of rejections is maintained in `rejections.codeRejections`.
4. **Ultra Review**:
   - One Ultra call (`nvidia/Nemotron-3-Ultra-550b-a55b`) reviews the original text, tuning overrides, computed facts, official controls, and candidate rewrites.
   - Evaluates:
     - Is the rewrite accurate?
     - Does it invent controls?
     - Is there a number or percentage mismatch?
   - Returns `ACCEPT` or `REJECT` with a reason.
5. **Conditional Retry**:
   - If code check fails OR Ultra reviewer rejects, exactly **ONE** retry is dispatched to Super with the rejection reason fed back.
   - The retried text is checked again by code and reviewed by Ultra.
   - Total retries per aid is strictly capped at 1.
6. **Output**:
   - Atomically written to `data/nemotron-review/aid-fix.json` with the original text, final rewrite, code check status, reviewer verdict, initial attempts, and retry counts.
   - `data/tutor/results.json` is never modified.

---

## Lead Run Budgets

The system is designed to operate strictly within the following maximum call budgets:
- **Ultra**: 2 initial calls (1 for `drift-judge` + 1 for `aid-fix` batch review) plus at most 3 retries (1 per aid if needed).
- **Super**: 3 initial calls (1 per aid) plus at most 3 retries (1 per aid if needed).

## How to Run

### 1. Offline Dry Runs
Prints prompt token estimates, computed facts, and extracted control keys without making any network calls:

```bash
# Dry run drift judge
npx tsx ai/cli/nemotron-review.ts drift-judge --dry-run

# Dry run aid fix
npx tsx ai/cli/nemotron-review.ts aid-fix --dry-run
```

### 2. Offline Injected Results (Testing)
Validates imported or mock answers completely offline without network or API keys:

```bash
# Validate drift judgments from an injected JSON answer
npx tsx ai/cli/nemotron-review.ts drift-judge --results-from /path/to/mock-drift.json

# Validate aid rewrites and reviews from an injected JSON answer
npx tsx ai/cli/nemotron-review.ts aid-fix --results-from /path/to/mock-aid.json
```

*(Note: The CLI strictly refuses to read any `.env` file passed to `--results-from`.)*

### 3. Live Execution (For the Lead Only)
Executes live model calls against Nebius Token Factory with credentials loaded from environment:

```bash
# Run Mode 1: Drift Judge
npx tsx --env-file=.env ai/cli/nemotron-review.ts drift-judge

# Run Mode 2: Aid Fix
npx tsx --env-file=.env ai/cli/nemotron-review.ts aid-fix
```

### 4. Verification Suite

```bash
# Run the dedicated nemotron-review unit test suite
node --import tsx --test ai/nemotron-review.test.ts

# Run the complete test suite across the repository
node --import tsx --test ai/*.test.ts

# Run TypeScript typecheck
npx tsc --noEmit
```

## Results of the live run (2026-10-30 00:48 UTC, one run each)

**1. Ultra judges the Spec Drift claims** (`data/nemotron-review/drift-judge.json`, one Ultra call, about 10.9K estimated prompt tokens).

| | Real drift | Doc vague | Not drift |
|---|---|---|---|
| Nemotron Ultra | 7 | 1 | 0 |
| Gemini 3.8 Flash (earlier) | 3 | 1 | 4 |

Agreement 4 of 8, Cohen's kappa 0.24 (weak). All 8 of Ultra's reasons passed the code check that the quoted text really occurs in the cited code or doc excerpt, yet **Ultra was wrong on claims 4, 5 and 6, and Gemini was right**, checked by hand: the `FEINT` action is handled (`game/src/ai.js:115`), `observedMoves` is capped at 8 (`ai.js:81`), and `attacksSinceKick >= 2` forces a kick (`ai.js:53`). So the code check proves a quote exists, not that the model read it correctly, and Ultra over-calls drift. The Spec Drift page therefore keeps the Gemini verdicts (which matched the hand check) and does not use Ultra's.

**2. Super fixes its own aid text, Ultra reviews it** (`data/nemotron-review/aid-fix.json`; the original `data/tutor/results.json` is unchanged).

- 3 aids, 0 code rejections, 2 reviewer rejections, 2 retries, all 3 accepted in the end.
- The fix that mattered: the guard aid said "reduce incoming damage by 80%" but its tuning (`rules.guardDamageMultiplier` 0.15) means 85% less damage; Super's rewrite says "take only 15% of incoming damage", which matches the number and passed both the code check and the reviewer.
- Limits: one run, three short texts; the reviewer is another Nemotron model, so its acceptance is a second opinion, not proof; the numbers were checked by code, the wording was not tested on players. The reviewer's `aidIndex` field is 0 for the second aid (a labeling quirk of the retry reviews; the verdicts are stored in aid order).
